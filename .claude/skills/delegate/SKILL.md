# delegate: 위임 브리프와 effort 판정

이 스킬은 routing.md §4~§7을 실행 수준으로 풀어 쓴 것이다. 매 위임마다 아래 워크시트로 effort를 정하고 템플릿을 채운다.

## 1. effort 판정 워크시트
각 항목에 점수를 매기고 가장 높은 등급을 택한다.

| 항목 | E1 low | E2 medium | E3 high | E4 xhigh |
|---|---|---|---|---|
| 범위 | 1~2파일 | 5파일 이하 | 여러 모듈 | 시스템 경계 넘음 |
| 명세 | 완전, 정답이 하나 | 분명, 구현 선택 약간 | 목표는 분명, 원인·방법 불명 | 트레이드오프 판단 필요 |
| 실패 비용 | 바로 드러남, 되돌리기 쉬움 | 테스트로 잡힘 | 런타임에서만 드러남(스레드, 성능, 보안) | 데이터 손실, 장치 손상, 외부 영향 |
| 자동 검증 | 있음 | 있음 | 부분적 | 없음 |

- 두 항목 이상이 E4면 Architect가 직접 맡을지 먼저 검토한다(§2 위임 금지 항목인지).
- `max`는 "사람 개입 없이 오래 파고들어야 하는 단일 문제"일 때만. 브리프에 사유 한 줄을 쓴다.
- 확신이 없으면 한 단계 위. 단, E1 작업을 E3로 보내는 식의 과잉 배정은 토큰 낭비다. 근거를 한 줄로 적어 보고에 포함한다.

## 2. 호출 방법
- Agent 도구 호출에 `subagent_type`(worker / verifier / researcher / designer / Explore), `model: "opus"`, `effort: "<등급>"`을 함께 넘긴다. 에이전트 파일의 effort는 기본값이고 호출 시 값이 우선한다.
- 독립 작업은 한 응답에서 여러 Agent 호출로 병렬 실행한다. 최대 5개.
- 결과를 이어서 쓸 에이전트는 완료 후 SendMessage로 같은 에이전트에 후속 지시를 보낸다(컨텍스트 유지).
- 실행 후 `/tasks`로 모델과 effort가 의도대로 적용됐는지 한 번 확인한다.

## 3. 브리프 템플릿
```
[목표] 한 문장. 무엇이 완료되면 끝인지.
[배경] 왜 하는지 두 줄 이내. 사용자가 이미 결정한 사항.
[입력] 파일 경로:줄 범위, 관련 심볼, 재현 명령, 참고 자료 경로.
[제약] 건드리지 말 파일, 유지할 동작, 스타일 규칙, 불변 조건(CLAUDE.md 항목 인용).
[완료 기준] 검증 가능한 항목 번호 목록. 실행할 검사 명령.
[반환 형식] 결론 / 변경 파일 / 실행한 검사와 출력 / 확신도 / 열린 질문. 과정 서술 금지.
[금지] push, 삭제, 범위 밖 수정, 설정 변경, 외부 전송 (허용할 항목만 명시).
[effort] <등급> — 사유 한 줄.
[승격 이력] (재위임일 때) 이전 시도, 실패 내용, 바뀐 지시.
```
서브에이전트는 대화 기록, 이미 읽은 파일, 호출된 스킬을 보지 못한다. 필요한 사실은 전부 브리프에 적는다. 긴 파일은 경로만 주고 읽게 한다.

## 4. 예시
**E1 (worker, low)**: "README의 `inhereted` 오타를 `inherited`로 고친다. 입력: README.md. 완료 기준: grep으로 오타 0건. 반환: 변경 파일과 grep 출력."
**E2 (worker, medium)**: "`SOFASocketSender`에 재연결 시도 횟수 Data 필드 `maxRetries`(기본 3)를 추가한다. 입력: src/ForceDimensions/SOFASocketSender.{h,cpp}, `connectToUE`. 제약: 패킷 포맷 변경 금지, 기존 Data 네이밍(`d_` 접두) 유지. 완료 기준: 1) 필드가 씬에서 설정 가능 2) 실패 시 maxRetries 번 재시도 후 경고 로그 3) 빌드는 불가하므로 컴파일 오류 가능성을 스스로 점검. 반환: 표준."
**E3 (worker, high → verifier, high)**: "햅틱 스레드가 종료 시 간헐적으로 크래시한다. 입력: OmegaDriver.cpp `updateForceFeedback`, 소멸자, `shouldStop`. 제약: 불변 조건(소멸자 순서, 플래그 제어) 유지. 완료 기준: 1) 경쟁 조건을 코드 근거로 특정 2) 최소 수정 3) 왜 안전한지 설명. 반환: 표준. 완료 후 verifier에 '이 수정이 여전히 크래시할 시나리오를 찾아라'로 교차 검증."
**연구 (researcher, medium)**: "논문 PDF를 발표용으로 분석한다. 입력: @papers/x.pdf. 반환: 기본 구조(문제, 주장, 방법, 결과 숫자, 한계, 발표용 그림 목록) + 페이지 출처."

## 5. 승격 사다리
1. 실패 1회: 같은 effort에서 브리프를 더 구체화해 1회 재시도(원인이 브리프 부족일 때만).
2. 실패 2회 또는 ESCALATE: 한 단계 위 effort로, 실패 내용을 [승격 이력]에 붙여 재위임.
3. 두 번 승격 후 실패: Architect가 직접 맡는다. 사용자 보고에 이력을 남긴다.
강등: 진행 중 기계적인 부분이 드러나면 쪼개서 E1으로 분리 위임한다.
